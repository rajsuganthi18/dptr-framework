## Abstract

Automated UI test suites frequently break when application UIs evolve, and naive repair heuristics risk masking real defects. We present DPTR, a prototype Defect‑Preserving Test Repair system implemented in Playwright + TypeScript. DPTR combines structural DOM deltas, pixel‑level visual similarity, and runtime invariants to decide conservatively between HEAL (repair) and REJECT_BUG (preserve failure). We contribute (1) the DPTR prototype and Playwright fixture that intercepts locator actions, (2) a CLI experiment runner that emits per‑case forensic artifacts (screenshots, diffs, JSON summaries) and supports canvas/region template matching, and (3) an initial pilot study comparing DPTR to a NO_HEAL baseline and an aggressive HEURISTIC healer.

In our small synthetic pilot (12 cases) the aggregated metrics were: False Healing Rate (FHR) = 0.5 for all engines; Defect Preservation Rate (DPR) = 0.5 for all engines; Repair Precision: NO_HEAL 0.5, HEURISTIC 1.0, DPTR 0.5. These pilot numbers are preliminary; the repository provides tooling to scale experiments, reproduce results, and produce plots and forensic bundles suitable for review.

## 1. Introduction

Reliable UI tests are critical for regression detection and developer productivity. When locators break due to benign UI updates (e.g., id renames, cosmetic CSS changes), fully automated repairs can restore tests but risk hiding real defects. DPTR aims to minimize false heals by combining complementary signals:

- DOM structural similarity (attributes, tag, text, spatial proximity),
- Pixel‑level visual similarity of element screenshots (pngjs + pixelmatch),
- Runtime invariants (clickability checks) and a canvas/region fallback using template matching.

The system emphasizes auditability: every repair attempt writes forensic artifacts (baseline and candidate images, diffs, and JSON metrics) so humans can validate repairs.

## 3. System Design and Implementation

### 3.1 Overview

DPTR is implemented as a Playwright fixture (`src/dptr-fixture.ts`) that intercepts locator actions. When a locator call fails, DPTR captures the baseline `LocatingContext` (tag, attributes, text, bounding box, screenshot) and searches for candidates on the mutated page. Candidates are scored and either a HEAL is performed (the repaired locator is used to run the intended action) or DPTR decides to REJECT_BUG and preserve the failure.

### 3.2 Signals

- DOM distance (`computeDomDistance`): composite of tag mismatch, attribute overlap (Jaccard‑like), normalized text similarity (Levenshtein), and spatial proximity. Produces a normalized distance 0..1 (lower = more similar).
- Visual similarity (`visualSimilarityFromBuffers`): pixelmatch-based comparison of element screenshots, producing 0..1 (higher = more similar). If size mismatches occur, a conservative low similarity is returned.
- Runtime invariant (`InvariantVerifier`): clickability tests (visibility, elementFromPoint/pointer-events) executed via Playwright.
- Canvas fallback: `findBestMatchOnPage` performs a coarse grid template search on full‑page screenshots to find a region matching the baseline screenshot; the template match score is used as a proxy invariant when no DOM selector exists.

### 3.3 Decision Rule

The prototype uses a conservative rule: prefer candidate if domDistance < 0.6 AND visualSimilarity > 0.45 AND invariantPassed == true. The composite confidence score is S = 0.6*(1 − domDistance) + 0.4*visualSimilarity. These thresholds are configurable and intended to favor defect preservation over aggressive healing.

### 3.4 Forensic Artifacts

Per run the system writes:

- `baseline.png`, `mutated.png` (full page),
- `candidate_*.png` and `diff_*.png` for visual comparisons,
- `summary.json` with metrics (domDistance, visualSimilarity, invariantPassed, confidenceScore, decision),
- `report.html` (optional human-readable view generated by downstream tools).

All experiments are reproducible: the CLI runner supports `--targets`, `--runs`, `--retries`, and `--outdir` which organize artifacts per case and run.

## 4. Experimental Methodology

### 4.1 Engines

- NO_HEAL: no repair attempt; baseline for defect preservation.  
- HEURISTIC: aggressive selector heuristics (id/class/text) that attempt repairs without visual or invariant validation.  
- DPTR: the full multi‑modal system described above.

### 4.2 Mutations and Targets

Pilot used built‑in synthetic mutations: ID rename, text change, overlay blocking interaction, and event handler removal. For reproducible experiments, `experiments/targets.sample.json` demonstrates the targets JSON format; the runner also accepts inline `baselineHtml` / `mutatedHtml` for local cases.

### 4.3 Metrics

- False Healing Rate (FHR) on BUG cases = (#BUG cases healed to PASS) / (#BUG cases).  
- Defect Preservation Rate (DPR) = 1 − FHR.  
- Repair Precision on UI_UPDATE cases = (#UI_UPDATE cases that pass after repair) / (#UI_UPDATE cases).

### 4.4 Statistical Considerations

The pilot is small; for GTV we will scale to N≥100 per engine and per mutation class, report Wilson 95% CIs for proportions, and use McNemar’s test for paired comparisons between engines.

## 5. Pilot Results

The pilot run (built-in mutations, N=12) produced the summary in `experiment-summary.json`. Key aggregated numbers:

- Total runs: 12
- FHR: NO_HEAL = 0.5; HEURISTIC = 0.5; DPTR = 0.5
- DPR: NO_HEAL = 0.5; HEURISTIC = 0.5; DPTR = 0.5
- Repair precision (UI_UPDATE): NO_HEAL = 0.5; HEURISTIC = 1.0; DPTR = 0.5

Notes: The HEURISTIC precision of 1.0 arises from the tiny sample; it does not imply general superiority. The pilot serves to validate tooling and reproducibility rather than to draw definitive conclusions.

### 5.1 Observations from Forensics

- Some failures stemmed from candidate-discovery timing (`page.evaluate` errors when the page context changed); we added defensive error handling and retries to the runner.  
- DPTR’s canvas fallback found coarse matches for region-like targets, enabling evaluation on canvas-style UIs, but it is intentionally conservative and may miss true positives until optimized.

## 6. Discussion

DPTR emphasizes explainability and conservatism. For many teams this operational mode is preferable: developers retain visibility into repairs and can audit artifacts before accepting changes. The main trade-offs are extra runtime (screenshots and pixel diffs) and sensitivity of visual checks to styling changes.

### 6.1 Strengths

- Audit trail for every decision (images + metrics).  
- Multi‑modal checks reduce dependance on brittle single-signal heuristics.  
- Extensible to canvas targets via template matching.

### 6.2 Limitations

- Visual similarity is brittle for large style/theme changes.  
- Template-matching needs optimizations (pyramidal search, cross-correlation) for scale.  
- Some demo tests experienced timing/context issues — these require robust synchronization and timeouts for production use.
